# The register

| Where | What | Written by |
| --- | --- | --- |
| `registry/config.json` (main) | The current and accepted versions with their digests, sentences and `flow` (`comment`: kleidos-cla posts the sentence as the signer, version 1; `signin`: the signer signs in with the identity-only app and nothing is posted, version 2), the served repositories with `auto_approve`, the exempt accounts by numeric id, `coverage_from`, `app_id`, `signin_client_id` (the sign-in app, once it exists) and `timestamping` (the RFC 3161 service, whether it is qualified, and its pinned roots under `tsa/`). Read by the bot (cached 60 s) and by the recorder. Schema: `schema/config.schema.json`. | The owner, signed commits |
| `registry/entities.json` (main) | Organizations that signed the entity version: name, version, digest, date, the account ids they cover with start and end dates. Schema: `schema/entities.schema.json`. | The owner, signed commits with an `entity:` subject |
| `signatures/individual/<github id>.json` (branch `signatures`) | One signature per account: schema 1 for an acceptance comment, schema 2 for a sign-in. Schema: `schema/individual.schema.json`. | `record.yml` only |
| `signatures/individual/<github id>.tsr` (branch `signatures`) | The RFC 3161 time-stamp response over the SHA-256 of that JSON file's bytes. | `record.yml` only |
| `coverage/<owner>/<repo>/<number>.json` (branch `signatures`) | The authors of one merged pull request and the version each had accepted. Schema: `schema/coverage.schema.json`. | `record.yml` only |

`cla.py record` runs in `record.yml` with the repository's own `GITHUB_TOKEN`. For a sign-in (`--kind signin`, version 2 on) it reads the signer's token from the event payload (never from the command line or the environment), masks it, and asks GitHub "Check a token" (`POST /applications/{client_id}/token`, Basic with the sign-in app's client id from `signin_client_id` and its secret from the environment `signin`); it refuses unless GitHub says the token is valid, is of that app, belongs to the account the Worker reported, a personal one, and was created at most two hours before GitHub's answer, and unless the version is the current one, its flow is `signin`, the repository is served and public and the pull request exists. The entry's `accepted_at` is the `Date` of that answer and `authorized_at` its `created_at`; `recorder_commit` is the commit of main the run executes. The grant is then deleted (`DELETE /applications/{client_id}/grant`), whatever the outcome. For a signature by comment it re-reads the comment from GitHub and refuses it if it was edited, is not on the pull request it names, was not written by a personal account, or, after Unicode NFC and whitespace collapsing (the same explicit list of white-space characters as the Worker, tested against `tests/normalize-vectors.json` on both sides), is not exactly the sentence of an accepted version; an existing record for the same or a later version is success without a commit. The record's `method` is `web` when the comment was posted through the app whose numeric id is `app_id`, and `comment` otherwise. For coverage it works out the authors of the merged pull request itself, by the same rule as the bot (opener dated by the pull request's creation, every commit author and `Co-authored-by:` co-author, merge commits included, less the exempt and the entity-covered), and writes nothing, opening an issue instead, if any of them has no signature or GitHub lists fewer commits than the pull request has (it lists 250 at most). Every write is one `createCommitOnBranch` commit, which GitHub signs: one coverage file, or one signature together with its time-stamp token. The token comes from the service in `timestamping`, over the SHA-256 of the file's exact bytes, with a nonce, and is verified (`openssl ts -verify` against the pinned roots, with the request's nonce, at the token's own time; for a qualified service also ETSI's best-practices policy `0.4.0.2023.1.1` and the qualified statement `0.4.0.19422.1.1`) before it is written. When the service does not answer (two tries, 15 s apart, as Sectigo asks of scripts), the signature is written without a token, a replaced record's stale token is deleted in the same commit, and `--kind stamp`, which `record.yml` runs daily, adds the missing tokens of records whose last commit is the recorder's, one commit each. Each target (kind, repository, pull request, comment) has its own concurrency group, so a burst of signatures never cancels a recording; runs for different targets retry when the branch moved under them. Only a refusal (exit 3) opens an issue; any other failure is left to the next dispatch, and the Worker's cron re-dispatches the coverage of a pull request merged in the last week that has none.

`cla.py verify` runs in `verify.yml` after every recorder run and weekly. It fails, and opens an issue, if the `signatures` branch is not linear; if a commit changes anything but one record, or one signature with its token (the signature added or changed, its token added, changed or, only when the signature is replaced, deleted; or a token added alone), deletes a record, or touches another path; if a time-stamp token on the branch does not verify over the record beside it, at the commit that wrote either, against the pinned roots; if a commit is not the recorder's (authored by `github-actions[bot]`, committed by GitHub and carrying GitHub's valid signature, as GitHub reports it, never as the git metadata says), the owner's own signed `redact:` and `entity:` commits excepted; if a record does not have the schema's exact shape (times as `YYYY-MM-DDTHH:MM:SSZ`, evidence addresses by pattern, integer ids) or names a version or digest that was never published; if a record added since the last clean run does not cite an existing, unedited acceptance comment by the same account, with the same text hash and creation time, and the successful `record.yml` run on `main` of this repository that recorded exactly that comment, or, for a sign-in (whose token is revoked, so there is nothing left on GitHub to re-read), the successful `record.yml` run on `main` named `Record signin <repo>#<pr> <id>` that ran the `recorder_commit` the record names, through the app `signin_client_id` names (what a GitHub-signed commit minted anywhere else cannot pass); if `record.yml` or `verify.yml` is not enabled; or if a pull request merged in a served repository since `coverage_from`, more than an hour ago, has no coverage file. The commit facts cost one GraphQL query per 100 commits; the cross-checks run only on the records added since the last clean run, whose head is kept in the Actions cache.

The Worker applies the same shape check and requires the last commit of a record to be the recorder's before the record counts, so a file pushed to `signatures` by anybody else never turns a check green.

## Serving a repository

A repository is served once it is listed in `served_repositories`. Its `auto_approve` lets the app approve the held fork runs of a pull request whose authors have all signed, unless the head commit changes `.github/` or a held run's jobs name a label other than GitHub's standard hosted runners (`ubuntu-*`, `windows-*`, `macos-*`). **Never set `auto_approve` to true on a repository whose workflows can reach a self-hosted runner** (the bench hosts, say): signing is not a trust signal, and the `.github/` rule does not cover the scripts and build files a workflow runs from the pull request. The job check is a second line only: GitHub may not list the jobs of a run that is waiting for approval.

## A new version of the agreement

1. Add `agreements/vN/` and its entry under `versions` (the digest, the files, the `flow`, the sentence), and deploy a Worker built with the new texts: the Worker bundles every published version, and the public pages and the sign page show the one `current_version` names.
2. When the text is approved, make it current in one commit of `registry/config.json`: add `N` to `accepted_versions` and set `current_version` to `N`. No deploy is needed. For a `signin` version the sign-in app must exist first (`scripts/create-signin-app.ts`, then `signin_client_id`); until then the site pauses signing rather than take the acceptance another way.
3. Once that is live, drop the old version from `accepted_versions` if everyone must sign again. Its records stay valid history: the verifier checks every record against `versions` (everything ever published), and only the bot and the recorder's coverage use `accepted_versions` to decide what counts now.

Removal at a signer's request (GDPR art. 17, within the limits of art. 17.3(e)) is an owner's commit with a `redact:` subject.
